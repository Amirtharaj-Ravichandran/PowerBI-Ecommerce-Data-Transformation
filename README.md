# PowerBI-Ecommerce-Data-Transformation
E-commerce data analysis using Power BI, focusing on data cleaning, transformation, calculated columns, data merging, aggregation, filtering, and data modeling using Power Query Editor.
**1. Project Description**
This project focuses on preparing and integrating an e-commerce sales dataset using Power BI and Power Query Editor. The assignment uses three source tables: List of Orders, Order Details, and Sales Target. The tables contain order dates, order identifiers, customer and location details, product categories and sub-categories, quantities, amounts, profits, and monthly sales targets. The main purpose is to transform raw data into a consistent structure that can support reliable analysis and reporting.
The work shown in the screenshots includes importing the CSV files, changing data types, renaming and formatting columns, creating a Location field by combining State and City, calculating Profit Margin, classifying records as Profit, Loss, or Break-Even, merging order information with order-detail records, removing duplicate rows, sorting and filtering records, and creating relationships in the model view. These activities correspond to the assignment requirements for data preparation, data cleaning, business-rule columns, data integration, aggregation, and data modeling.
****Work Completed Based on the Screenshots**
Data import: The three CSV datasets—List of Orders, Order Details, and Sales Target—are shown in Power Query Editor.
Data transformation: The Order Details table has numeric data types applied to Amount, Profit, and Quantity. Customer names are formatted to proper case, and State and City are combined into a Location column.
Calculated columns: A Profit Margin column is created using Profit divided by Amount, multiplied by 100. A conditional column classifies negative profit as Loss, zero profit as Break-Even, and positive profit as Profit.
Merging and duplicate handling: The screenshots show Order Details expanded into a merged query and a Remove Duplicates step. A Tamil Nadu filter is also shown in the merged data.
Data model: The model view shows relationships between List of Orders and Order Details, and between Order Details and Sales Target. Relationship configuration needs further validation before the model is considered complete.
**Key Insights and Observations**
•	The data is suitable for joined analysis. Order ID is used to connect order-level information with individual order-detail rows. This allows customer and location information to be examined alongside amount, profit, quantity, category, and sub-category.
•	Profit performance varies across records. The visible sample contains both negative and positive profit values, as well as zero-profit records. The Profit Status column is therefore useful for distinguishing losses, profitable transactions, and break-even transactions. The screenshots do not provide enough complete summary results to identify the best-performing category or total profit.
•	Profit Margin needs careful interpretation. The formula shown is (Profit / Amount) × 100. Some records have negative margins, and a record with Amount equal to zero would need a safe handling rule to avoid a division error. Negative or unusually large percentages should be checked against the source data and business definitions.
•	Location filtering enables regional analysis. The screenshot shows a filter for State = Tamil Nadu, with Chennai appearing as the city in the displayed records. This demonstrates how the data can be narrowed to a state for regional analysis; it does not establish statewide sales performance by itself.
•	Data-quality issues are visible in List of Orders. The screenshots show a date-conversion step producing Error values for many rows after the first several records. The row count also shows 560 rows after a step intended to keep the first 500 rows, suggesting that the row-limiting/header steps should be reviewed. These issues should be fixed before using the table for analysis.
•	The Sales Target dates require validation. The Sales Target preview displays dates in 2026, while the List of Orders preview shows order dates in 2018. This may reflect source data or date interpretation/locale issues. Confirm the intended month and year values and ensure the target period matches the order data before calculating target achievement.
•	The model relationships should be checked. The model screenshot appears to show a many-to-many relationship between Order Details and Sales Target. Since both tables can contain repeated Category values, connecting them directly by Category can create ambiguous filtering or incorrect totals. A distinct Category dimension, and a proper month/date dimension where needed, would generally provide a safer model design.
**Recommendations for Improvement**
1.	Promote the first row to headers immediately after importing List of Orders, then verify the column names before applying further transformations.
2.	Use the correct locale when converting Order Date to Date. For dates formatted as DD-MM-YYYY, select the appropriate locale or parse the date consistently, then confirm that no Error values remain.
3.	Apply Keep Top Rows = 500 to the data rows after header promotion, and verify the final row count is exactly 500 (unless the assignment interprets the limit differently).
4.	Set Amount and Target to Fixed Decimal Number as requested in the questionnaire. Set Profit and Quantity to suitable numeric types as well.
5.	Rename the conditional column from the default name Custom to Profit Status, and rename the merged query to Orders Data as required.
6.	Check missing values and duplicates in all three tables. Remove duplicates only where the full row is genuinely duplicated; do not remove legitimate repeated Order IDs from Order Details because one order can contain multiple products.
7.	Protect the Profit Margin calculation against Amount = 0 and format the resulting values as percentages for readability.
8.	Validate that the Sales Target month/date values match the order-data period and use consistent month-start dates or a calendar table.
9.	Review Manage Relationships. Prefer a one-to-many relationship from a unique Order ID table to Order Details, and use a distinct Category dimension to connect category-level targets. If targets are monthly, include a month/date dimension so targets filter by both category and month.
10.	After correcting the data, refresh the model and test totals against the source files. Capture updated screenshots of the cleaned queries and final model view for submission.
**Conclusion**
This Power BI assignment demonstrates the key stages of preparing e-commerce data for analysis, including importing multiple CSV files, transforming data types and text fields, creating location and profit-related columns, merging order and order-detail information, removing duplicates, filtering records, and establishing model relationships. The Profit Margin and Profit Status columns add useful business meaning to the transaction data, while location and category fields support further analysis by region and product group. However, the screenshots also reveal items that should be corrected before the model is treated as analysis-ready: date-conversion errors in List of Orders, a row count that does not appear to match the 500-row requirement, Sales Target dates that differ from the order-date period, and a relationship that appears to be many-to-many. Once these data-quality and modeling issues are resolved and the relationships are validated, the prepared model can provide a more reliable basis for evaluating sales, profit, product performance, and target achievement.
